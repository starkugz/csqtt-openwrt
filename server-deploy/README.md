# Серверное развёртывание CSQTT (установка, обновление, откат)

Самостоятельный инструмент для безопасной замены **серверного бинарника CSQTT**
в уже развёрнутом окружении и точного отката. Это часть выпуска **CSQTT 2.0**.

Скрипт: [`server-deploy.sh`](server-deploy.sh).

## Подтверждённая платформа и схема

Схема определена по официальному `deploy.sh` серверного архива community:

| Параметр | Значение |
|---|---|
| ОС | Linux (Ubuntu/Debian), **systemd** |
| Архитектура ядра | x86-64 (проверено); arm64 также принимается, если совпадает с хостом |
| Служба systemd | `csqtt` |
| Установленный бинарник | `/usr/local/bin/csqtt` |
| Каталог конфигурации | `/etc/csqtt` |
| Интерфейс | `csqtt1` |
| UDP-порт peer | `46000/udp` |
| TCP-порт панели | `46002/tcp` |

Docker-контейнер — **альтернативная** схема из архива, но она не навязывается:
инструмент работает только по факту установленной в системе службы `systemd`.
Ни версия ядра (`2.1.9`/`2.5.0`), ни строки вида «2.5.1» инструментом не
присваиваются — он лишь фиксирует SHA-256 конкретного входного файла.

## Два серверных варианта

Инструмент принимает бинарник любого из двух серверных вариантов выпуска:
**2.1.9** (официальный закреплённый релиз upstream, SHA-256
`9740816075518c9d1d09524db0a9abb48a73b554a8dba6963f40b800ce65f9d3`) и
**2.5.1** (база CSQTT 2.5.0 + community-патч, SHA-256
`6bb29d0ea9ac47fcbd11d118022b9dba6dc309dc121491d73e6208db60cb9d35`). Примеры
ниже используют 2.5.1; для 2.1.9 подставьте его SHA-256. Как получить бинарник
2.1.9 из официального APK — в [инструкции для сервера](../docs/server.md).

## Границы инструмента

- Инструмент **не разворачивает CSQTT с нуля**. NAT/firewall/sysctl/сертификаты/
  unit/конфигурацию создаёт официальный `deploy.sh` из архива. `server-deploy.sh`
  заменяет **только** бинарник уже существующей службы.
- Инструмент **не читает, не печатает и не передаёт секреты**: каталог
  конфигурации при резервном копировании только упаковывается как есть.
- Никакого фиктивного контроля версии/здоровья: проверяются реальные признаки —
  состояние `systemd`, живой `MainPID`, наличие интерфейса, слушающийся TCP-порт
  панели и (необязательно) внешняя команда здоровья.
- Производственная установка — только в отдельном согласованном окне. Здесь
  выполнялась лишь локальная симуляция (см. «Статус проверки»).

## Требования

- Linux с systemd и работающим `systemctl`.
- `sha256sum` (или `shasum`), `tar`, `flock`, `od`, `head`.
- Права на замену файла в `/usr/local/bin` и на перезапуск службы (обычно root).
- Официальный `deploy.sh` уже установил службу и конфигурацию.

## Команды

Все действия возвращают машиночитаемый **маркер в stdout**; человекочитаемые
сообщения идут в **stderr** и в лог `0600`. Секретов в выводе нет.

```sh
# 1. Предварительная проверка (dry-run, ничего не меняет).
sudo bash server-deploy.sh preflight \
  --binary /path/csqtt-server-linux-amd64 \
  --sha256 6bb29d0ea9ac47fcbd11d118022b9dba6dc309dc121491d73e6208db60cb9d35 \
  --dry-run

# 2. Первая укладка бинарника в существующее окружение.
sudo bash server-deploy.sh install \
  --binary /path/csqtt-server-linux-amd64 \
  --sha256 6bb29d0ea9ac47fcbd11d118022b9dba6dc309dc121491d73e6208db60cb9d35 \
  --yes

# 3. Обновление уже установленного бинарника.
sudo bash server-deploy.sh update \
  --binary /path/csqtt-server-linux-amd64 \
  --sha256-file /path/csqtt-server-linux-amd64.sha256 --yes

# 4. Статус (только чтение, без изменений и без секретов).
sudo bash server-deploy.sh status

# 5. Проверка установленного файла по хешу и здоровья.
sudo bash server-deploy.sh verify \
  --sha256 6bb29d0ea9ac47fcbd11d118022b9dba6dc309dc121491d73e6208db60cb9d35

# 6. Точный ручной откат к последней резервной копии.
sudo bash server-deploy.sh rollback --yes

#    ...или к конкретной резервной копии:
sudo bash server-deploy.sh rollback --backup /var/lib/csqtt-deploy/20261106-120000-update-12345 --yes
```

`--dry-run` (`-n`) применим к `preflight`, `install`, `update`, `rollback`.

### Ключевые параметры

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `--binary PATH` | входной серверный бинарник (ELF) | — |
| `--sha256 HEX` | ожидаемая SHA-256 (обязательна, если нет `--sha256-file`) | — |
| `--sha256-file PATH` | файл с SHA-256 (берётся первый хеш) | — |
| `--service NAME` | имя службы systemd | `csqtt` |
| `--target PATH` | путь установленного бинарника | `/usr/local/bin/csqtt` |
| `--config-dir PATH` | каталог конфигурации | `/etc/csqtt` |
| `--unit PATH` | файл unit (иначе проверяется `systemctl cat`) | — |
| `--iface NAME` | интерфейс для health-check (пусто — не проверять) | `csqtt1` |
| `--web-port N` | TCP-порт панели (0 — не проверять) | `46002` |
| `--health-cmd CMD` | дополнительная проверка здоровья (exit 0 = здоров) | — |
| `--backup-root PATH` | корень резервных копий | `/var/lib/csqtt-deploy` |
| `--state-dir PATH` | каталог состояния/журнала | `<backup-root>/state` |
| `--backup DIR` | копия для `rollback`/`verify` | последняя |
| `--stability-seconds N` | окно стабильности после запуска | `4` |
| `--health-timeout N` | бюджет ожидания health-check, с | `30` |
| `--no-backup-config` | не копировать каталог конфигурации | — |
| `--restore-config` | при `rollback` восстановить и конфигурацию | — |
| `--yes` / `-y` | без интерактивного подтверждения | — |
| `--force` | заменить, даже если SHA уже совпадает | — |

## Что делает установка/обновление

1. **Предварительная проверка:** ОС = Linux; архитектура хоста среди
   x86-64/arm64/armv7; найден `systemctl`; входной файл — ELF с `e_machine`,
   совпадающим с хостом; SHA-256 **обязательно** совпадает; найден unit
   (`--unit` или `systemctl cat`); существует каталог для бинарника.
2. **Идемпотентность:** если установленный файл уже имеет тот же SHA и служба
   здорова — выводится маркер `CSQTT_SERVER_UP_TO_DATE` и ничего не меняется
   (без `--force`).
3. **Резервная копия:** каталог `0700` с прежним бинарником (`0700`),
   `previous_present`/`previous-sha256`, параметрами службы и архивом
   конфигурации `config.tar.gz` (`0600`).
4. **Атомарная замена:** временный файл в том же каталоге + `mv` (rename),
   права `0755`, владелец берётся с прежнего файла.
5. **Перезапуск** ровно согласованной службы (`systemctl restart`).
6. **Health-check:** `active`/`running`, живой `MainPID`, интерфейс
   `--iface`, слушающийся `--web-port`, необязательный `--health-cmd`; затем
   окно стабильности `--stability-seconds` и контроль, что `NRestarts` не вырос.
7. **При провале — автоматический откат** к прежнему бинарнику и повторный
   запуск службы; если откат не удался, печатается точная команда ручного отката
   и код `31`.

## Резервные копии и состояние

- Корень копий: `/var/lib/csqtt-deploy/<ГГГГММДД-ЧЧММСС>-<действие>-<pid>/`
  (`0700`), файлы внутри — `0600`.
- Состояние: `/var/lib/csqtt-deploy/state/`:
  - `last-backup` — каталог, выбранный для `rollback` по умолчанию;
  - `installed-sha256` — SHA-256 последней успешной установки;
  - `deploy.log` — журнал (`0600`);
  - `lock` — `flock` против одновременных запусков.

## Коды возврата (контракт автоматизации)

| Код | Значение |
|---|---|
| `0` | успех |
| `2` | ошибка использования (неизвестный параметр/действие, отмена) |
| `20` | предварительная проверка не пройдена (ОС/архитектура/ELF/SHA/unit) |
| `30` | установка/health не удались, **автоматический откат выполнен** |
| `31` | установка не удалась и **откат тоже не удался** |
| `40` | уже выполняется другой запуск (занят `lock`) |
| `50` | внутренняя ошибка |

## Маркеры (stdout)

| Маркер | Когда |
|---|---|
| `CSQTT_SERVER_PREFLIGHT_OK\|<служба>` | dry-run прошёл |
| `CSQTT_SERVER_PREFLIGHT_FAILED\|<служба>` | проверка не пройдена |
| `CSQTT_SERVER_DRY_RUN\|<служба>` | изменения не вносились |
| `CSQTT_SERVER_UP_TO_DATE\|<служба>\|<sha>` | уже установлено |
| `CSQTT_SERVER_DEPLOY_OK\|<служба>\|<sha>` | установка/обновление успешны |
| `CSQTT_SERVER_ROLLED_BACK\|<каталог>` | откат (авто или ручной) выполнен |
| `CSQTT_SERVER_ROLLBACK_FAILED\|<каталог>` | откат не удался |
| `CSQTT_SERVER_VERIFY_OK\|<служба>` / `..._FAILED\|...` | результат `verify` |
| `CSQTT_SERVER_STATUS\|<служба>\|<состояние>` | результат `status` |

## Точный откат

Откат восстанавливает **прежний бинарник** из выбранной копии и перезапускает
службу. При `--restore-config` дополнительно распаковывается `config.tar.gz`.
Перед откатом текущее состояние сохраняется как новая копия `pre-rollback`,
поэтому откат можно безопасно повторить (в т.ч. откатить сам откат).

```sh
# последняя копия (по умолчанию):
sudo bash server-deploy.sh rollback --yes
# конкретная копия:
sudo bash server-deploy.sh rollback --backup /var/lib/csqtt-deploy/<...> --yes
```

Если установка была первой (прежнего бинарника не было), откат удаляет
установленный файл и останавливает службу — это не выдаётся за успешный запуск.

## Безопасность

- Секреты (пароли, токены, ключи, VK-хеши) не читаются, не печатаются и не
  передаются в аргументах командной строки; содержимое конфигурации не выводится
  ни в stdout, ни в stderr, ни в лог.
- Каталоги копий — `0700`, файлы — `0600`; журнал — `0600`.
- Проверка целостности опирается на **SHA-256 входного файла** (подпись в
  поставке недоступна). Хеш обязателен: без него установка отклоняется.
- Лицензия серверного бинарника — **PolyForm Noncommercial 1.0.0**
  (см. `../NOTICE.md`). Инструмент её не заменяет и
  Required Notice не удаляет.

## Статус проверки (честно)

- **Выполнено локально:** полный цикл на временной файловой системе, все ветки
  (dry-run, новая установка, обновление, повторный запуск, неверный SHA,
  несовместимая архитектура, провал health-check с авто-откатом, точный ручной
  откат, `status`, `verify`).
- **BLOCKED:** живая установка/обновление на сервере. Живая приёмка
  требует отдельного согласованного окна; доступ к серверу сам по себе не
  является разрешением его менять.
